# Сессионные OHLCV: аудит и исправление 15.11.2026

Версия терминала **0.2.26**. Исходная точка: `896fc1367e997257e13e00b69059b2615541cfc3`, проверенная перед изменением через `origin/main`. Задание пользователя: отдельные биржевые календари, H4 по торговым часам, согласованные D/W/M, отсутствие look-ahead и безопасная миграция кэша. Это изменение подготовки данных, не математического движка.

## До изменения

Активный Finam-путь получал **нативные M1/M5/H1/H4/D/W/M**, записывал их в `finam_candles_v1.sqlite3` и передавал анализатору. Нельзя утверждать, что прежний Finam H4 всегда собирался самим терминалом от московской полуночи: универсальный `market_data.aggregate/period_floor` существовал, но активный Finam-путь его не вызывал. Отдельный старый MOEX-путь имел свою агрегацию; он не является поставщиком текущих 38 инструментов.

`finam_bar` сохранял timestamp провайдера и назначал номинальное окончание `+4h`, `+1d`, `+7d` или следующий месяц. Это не доказывает биржевое закрытие, принадлежность ночных торгов к trading date, короткие дни и DST. `ExchangeClock` обслуживал отображение/VWAP, но не был полным историческим календарём OHLCV. Binance предоставлял все семь нативных периодов, с фактическим `closeTime`.

Исходная SQLite не хранила доказательство, когда незавершённая свеча была повторно получена после закрытия. Простой перевод часов мог сделать сохранённый черновик подтверждённым. Обычный поток мог переписать ранее закрытую исходную свечу. Старшие периоды не имели отдельной версии календарной политики.

## Новая конструкция

- `trading_calendar.py`: IANA-зона, **торговая дата**, один или несколько непрерывных сегментов, праздники/короткие дни и подтверждённые изменения расписания. `TradingSession.buckets(240)` расходует четыре **торговых** часа, переносится через внутрисессионный перерыв и оставляет короткую последнюю свечу. Между торговыми днями свеча не переносится. Расширение — датированные интервалы `TradingCalendar.overrides` через фабрику календаря, без новой настройки в UI.
- `session_candles.py`: общий расчёт канонических H1/H4, сессионного D и W/M из этих D. H1 тоже нормализуется, чтобы собственный график и старшие родители использовали одну сессию. Источник внутри одной свечи выбирается целиком M1 → M5 → H1; смешанную исходную OHLC нельзя разрезать в 09:30 или на произвольной границе H4. Допустимо сократить номинальное окончание последнего исходного бара до подтверждённого закрытия рынка.
- D Finam получает приоритет **после** совпадения с полной суммой той же сессии по OHLCV. Несовпадение фиксируется `native_daily_session_mismatch`, используется явно определённая сессионная сумма. Совпадение чисел не заменяет дальнейшую сверку самого режима сессии с TradingView. Native Binance H4/D принимаются только на точных UTC-границах; W/M строятся из D.
- W/M группируются по **trading date**, OHLC первой/максимума/минимума/последней D, объём — сумма D в одинаковых единицах одного источника. Sunday evening CME относится к Monday trading date, даже на границе месяца. Начало — начало первой сессии, scheduled close — конец последней. Неизвестные будущие внутренние часы праздника не блокируют текущий черновик, если обе границы периода известны; наступивший непроверенный день уже включать нельзя.
- У формирующейся свечи scheduled close остаётся в будущем. Её исходный снимок не может содержать окончательные значения, полученные позже момента наблюдения. Для закрытого источника требуется наблюдение после эффективного окончания; перевод часов сам по себе не подтверждает черновик. Поток не переписывает запечатанную исходную свечу; расхождение запускает HTTP-восстановление. Авторитетная HTTP-коррекция истории разрешена.
- Пропуски подтверждаются точным покрытием исходных интервалов либо успешным ограниченным HTTP-ответом. Пустой ответ/обрезанный возрастом диапазон не сертифицирует отсутствующую историю. Не создаются свечи с нулевой ценой или переносом предыдущего close. При разрыве сохраняется последний полный непрерывный суффикс аналитического контекста, а сырые данные остаются в базе. Дубликаты устраняет normalize, сортировка ведётся по UTC-инстантам, включая повторяющийся час DST.

## Хранилище, обновления и производительность

Алгоритм `session-ohlcv-1`, календарь `sessions-2026-11-15.1`. `session_store.py` добавляет таблицы `candle_source_observations`, `candle_source_revisions`, `candle_source_coverage`, `session_series_cache`. Исходная `candles` сохраняется. Производные H1/H4/D/W/M публикуются **одной семейной записью** с версией/хешем календаря, ревизией источника и временем наблюдения. Смена политики или повреждение производного JSON приводит к пересчёту из исходных данных. Чтение исходных свечей и их метаданных — одна SQLite snapshot-транзакция; при конкурентном изменении старый результат не записывается в новый кэш.

Legacy-барам без времени получения не приписывается подтверждение: нужна первая ограниченная HTTP-перепроверка. Затем сохраняются overlap последних трёх исходных свечей, обычные TTL, контроль полного рабочего окна раз в сутки и восстановление после разрыва. Старые native H4/W/M больше не запрашиваются активным Finam-путём без необходимости; native D остаётся кандидатом для сверки. Подписки Finam M1/M5/H1/D, Binance M1/M5/H1/H4/D + LAST.

Архив подкачивается после публикации результатов скринера по одному окну до 30 дней за фоновый проход: M5 для акций, H1 для фьючерсов. Курсор SESSION_M5/SESSION_H1 сохраняется. Он ограничен проверенной календарной историей и первым известным D конкретного контракта. Пустое окно останавливает поиск как эвристика, **не как доказательство отсутствия всех более ранних данных**. Полный архив не скачивается заново при каждом запуске. Единая очередь Finam/приоритет графика сохранены.

Флаги/настройки/цвета/версия UI не добавлены. Пользовательский сдвиг/zoom остаются в прежней логике сохранения вида. Подробности — только безопасные фиксированные коды в локальном журнале, без token/JWT/account/body/URL. Календарные справочники используются только для расписания; **экспирации по-прежнему исключительно Finam**, MOEX ISS котировки — только для топ-20.

## TradingView: что подтверждено и что требуется

**Прямой числовой паритет TradingView не подтверждён:** доступного эталонного экспорта свечей пользователь не предоставил. Официальная документация объясняет сессионное время, но не доказывает OHLC конкретного фида/контракта. Не заявляется, что по всем биржам TradingView обязательно использует одинаковую схему H4.

Добавлен `tools/compare_session_csv.py`: сравнивает начало/конец, OHLC и опционально V; экспорт без `time_close` не позволяет подтвердить окончание. Требуются CSV того же точного контракта (не continuous вместо серии), провайдера, adjusted/unadjusted режима и session setting, по H4/D/W/M: обычный день, week/month boundary, праздник/short day, DST. Для forming-эталона нужен снимок исходных данных **в тот же asof**, не позднейший финальный OHLC. Входные даты обязательно timezone-aware или Unix.

Пример из корня проекта (пути заменить своими CSV):

```powershell
python -m tools.compare_session_csv --symbol 'AAPL@XNGS' --timeframe H4 --source 'M5=provider_m5.csv' --asof '2026-11-13T23:59:59Z' --reference 'tv_h4.csv' --compare-volume --output 'comparison.json'
```

`full_parity_confirmed` относится **только к переданному образцу** с доступными окончаниями и сопоставимым V; это не сертификация всего архива. CLI не импортирует TradingView в рабочий терминал и не делает сетевых запросов.

Оставшиеся ограничения: CME product-specific праздничные часы; ICE March DST и отдельные декабрьские даты; MOEX до подтверждённых режимов/до 2026; режим аукциона US; отсутствие TV-эталона. При этих условиях инструмент/период может быть недоступен, а не приближён. Следующее расширение календаря требует официального product/date расписания и новой версии политики.
